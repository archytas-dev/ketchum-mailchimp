## 5. Cómo re-verificar (Paso 1.5, Paso 2, Paso 4, Paso 6)

El hash plano no sirve para comparar contra un día posterior. Usar **el mismo corte** que este
baseline, que congela el universo de filas:

```sql
-- CORTE FIJO DEL BASELINE. No cambiar este valor al re-verificar.
with corte as (select timestamptz '2026-09-15 14:10:41.911869-03' as ts)
select 'clippings' t, count(*) filas,
       md5(coalesce(string_agg(md5(x::text),'' order by md5(x::text)),'')) hash
  from public.clippings x, corte where x.created_at <= corte.ts
union all select 'notes', count(*), md5(coalesce(string_agg(md5(x::text),'' order by md5(x::text)),''))
  from public.notes x, corte where x.created_at <= corte.ts
union all select 'notes_precarga', count(*), md5(coalesce(string_agg(md5(x::text),'' order by md5(x::text)),''))
  from public.notes_precarga x, corte where x.created_at <= corte.ts
union all select 'activity', count(*), md5(coalesce(string_agg(md5(x::text),'' order by md5(x::text)),''))
  from public.activity x, corte where x.created_at <= corte.ts
union all select 'reportes', count(*), md5(coalesce(string_agg(md5(x::text),'' order by md5(x::text)),''))
  from public.reportes x, corte where x.created_at <= corte.ts
order by 1;
```

**Qué significa cada resultado:**

- **Hash acotado igual** → ninguna fila preexistente se modificó ni se borró. Es la garantía que
  pide el runbook. Filas nuevas por encima del corte son la v3 operando: esperadas.
- **Hash acotado distinto** → algo reescribió o borró historia. **Parar, guardar el diff, pedir
  revisión** (regla 6).
- Las tablas de §2.2 (config) sí admiten comparación de hash plano, porque no se escriben solas.

`exports`, `summaries` y `user_clipping_state` no tienen `created_at` en todas sus filas útiles
para este corte; se comparan por hash plano y se interpreta un cambio junto con la actividad del
equipo ese día.
